# V2 retained journal

V2의 선택형 Linux 저장 모드는 완료된 응답을 원본 원장과 체크포인트에 보존하면서 메모리에 유지하는 이벤트·응답 시도·관측을 각각 8,192개 이하로 제한한다. 기존 파일 형식은 기본값이며, 새 모드는 `policy-edge -v2-state <path> -v2-retention`으로 명시적으로 활성화한다. 원본 Tester 파일과 SDK의 인증·객체 접근 규칙을 변경하지 않는다.

## 보존과 복구

처음 활성화하면 기존 원장 바이트를 `<path>.retained/segment-000000.jsonl`에 보존하고 `<path>`를 저장소 식별자·레지스트리·최초 원장의 해시·설정에 결합된 루트 표식으로 바꾼다. 이전 바이너리나 일반 `Open`으로 이 표식을 열 수 없다. 표식이 유실되어도 남아 있는 보존 디렉터리를 빈 저장소로 초기화하지 않는다.

체크포인트는 이전 세그먼트의 해시, 전역 순번과 해시 체인, 정책 소유권·epoch·예산·작업·intent·L3 상태, 보류 응답, 누적 응답 결과를 포함한다. 5초 증명 유효 기간을 지난 완료 응답만 접을 수 있다. 진행 중인 응답과 정책 판단에 필요한 참조는 유지한다. 과거 요청 ID와 완료 콜백의 중복·충돌·이전 프로세스 검사는 체크포인트의 정확한 원본 값으로 확인한다. SHA 접두어 색인은 조회 최적화에만 사용한다.

저장 순서는 이전 원장 동기화 → 새 불변 체크포인트 동기화 → 빈 후속 세그먼트 동기화 → `CURRENT` 원자 교체·디렉터리 동기화다. 재시작은 모든 원본 행의 서명과 전역 체인을 재생하고 체크포인트 전체를 다시 계산한다. 진행 중이던 외부 작업은 재전송하지 않고 `interrupted_unknown`으로 복원한다. 새 writer 시작도 원장에 기록하므로 이후 체크포인트에서 동일하게 재현된다.

회전 시 이전 세그먼트는 64 KiB 버퍼로 모든 바이트를 SHA-256 해시한다. 일반 파일·크기·파일 정체성을 확인하고, 읽은 길이가 동기화된 기록 길이와 다르면 writer를 차단한다. 전체 세그먼트를 메모리에 보관하지 않으며 해시 대상이나 동기화 횟수를 줄이지 않는다.

체크포인트는 한 번 JSON 인코딩한 동일 바이트를 용량 예약 검사와 불변 파일 발행에 사용한다. 발행 단계에서 다시 인코딩하지 않으며, 줄바꿈·저장 형식·동기화·`CURRENT` 교체 순서는 유지한다.

자동 복구는 완전한 체크포인트와 빈 후속 세그먼트처럼 결과가 명확한 중단만 처리한다. 부분 원장, 조작된 스냅샷, 비어 있지 않은 예상 밖 후속 세대, 포인터 후퇴는 차단한다. 원본을 임의로 자르거나 삭제하지 않는다.

## 용량과 운영 한계

기본값은 세그먼트 16 MiB, 보존 저장소 전체 8 GiB, 최대 256세대다. 완료된 원본 기록도 자동 삭제하지 않으므로 무제한 운영을 의미하지 않는다. 요청을 수락하기 전에 보류 응답마다 완료 기록용 공간 2,048바이트를 확보한다. 세대·용량 소진 시 새 수락을 차단하고 이미 수락한 쓰기의 기록 공간을 유지한다. 실제 I/O 실패는 저장소를 차단한다.

Linux 보존 모드는 작업 목록에 사건을 최대 1,024개 유지한다. 새 사건이 필요해 상한에 도달하면, 증명 기한이 지났고 현재 보존된 전체 사건 이력이 정상 200으로 확인되는 가장 오래된 사건을 교체할 수 있다. 미완료 응답, 정책 또는 정책 이력, Decisions·L3 작업에 연결된 사건과 이력이 잘린 사건은 유지한다. 교체는 새 서명 관측과 같은 저널 레코드로 기록된다. 봉인된 원본 증거와 사후 응답 감사 내보내기는 유지된다. 조건에 맞는 사건이 없으면 새 사건 경로는 503을 반환한다. 기존 비보존 모드의 사건 상한은 512개다.

교체된 사건은 `/v2/cases`의 작업 목록에서 빠지며, 같은 세션의 새 요청은 새 사례 버전을 연다. 교체가 기록된 저널에는 `retired_case`를 이해하는 writer와 읽기 전용 검증기가 필요하다. 새 버전은 기존 필드가 없는 저널도 재생한다. 최초 교체 후 이전 writer로 되돌릴 운영 계획이 있다면 업그레이드 전 중지 상태의 원본 저널을 별도로 보존한다.

신규 정책 명령 설치 상한 4,096건, Decisions 작업 1,024개, L3 작업 128개 및 일일 API 예산을 적용한다. 보존 모드의 엣지 증거 스트림은 각각 512 MiB다. 운영자는 저장 용량과 작업 상한을 각각 감시한다.

인증이 필요한 비공개 `/v2/status`의 `outcome_audit.retention`에 현재 세대, 활성·누적 응답 수, 사용량과 한도를 제공한다. `hot_cases`와 `max_hot_cases`는 작업 사건 수와 상한이다. `pending_unknown`, `audit_available`, `/v1/status`의 증거 저장 실패와 큐 누락도 함께 확인한다. Windows에서는 기존 저장 모드를 사용한다.

신규 보존 저널을 만들 때 `-v2-retention-config /config/v2-retention.json`으로 세그먼트 크기, 저장 한도, 최대 세대 수를 지정할 수 있다. 예제 [config.v2-retention.example.json](../config.v2-retention.example.json)의 값은 기존 기본값과 같다. `-v2-retention`과 `-v2-state`가 모두 필요하다. 생성 시 설정은 저널에 고정되며 기존 저널의 재시작과 복구에도 동일한 값을 지정한다. `-protection-check`에서 파일 검사와 선택한 한도를 확인할 수 있다.

`remaining_storage_bytes`와 `remaining_generations`는 설정 대비 잔여량이다. 실제 디스크 여유, 새 체크포인트와 진행 중인 응답의 공간 예약을 포함한 수용 가능 요청 수는 별도로 측정한다. `/v1/status`의 `coverage_evidence_storage`와 `protection_evidence_storage`는 계측 옵션과 관계없이 구성된 증거 저장소 한도를 보여준다. 해당 저장소의 한도는 V2 설정으로 변경되지 않는다.

`/v2/status`의 `outcome_audit.policy_command_budget`에는 명령 기록 수(`recorded`), 신규 정책 설치 상한(`install_limit`, 4096), 상한 도달 여부(`new_installs_at_limit`)가 표시된다. 상한에 도달하면 native·운영자·AI의 새 정책 설치와 갱신을 중단한다. 저널이 쓰기 가능한 동안 소유권과 현재 세대를 확인한 정책 해제는 계속 기록할 수 있다. 기록 수는 해제로 인해 설치 상한을 넘을 수 있다. 상한 상태에서는 현재 정책과 저장소 상태를 확인하고 운영 대응을 시작한다. 이 개수는 저널 용량 및 활성 정책 수와 별도다.

## 검증과 성능 옵션

writer를 정상 종료한 후 다음 명령으로 원본을 변경하지 않고 서명·원장·체크포인트와 실제 응답 쓰기를 검증할 수 있다. 다른 프로세스가 저장소를 쓰는 동안 검증기는 실행을 거부한다. 출력은 새 외부 파일이어야 한다.

```sh
bin/v2-journal-check -state /data/v2.jsonl \
  -protection-registry /config/registry.json \
  -responses /evidence/new-verified-responses.jsonl
```

### 정지한 writer의 백업과 승계

1. 진입 트래픽을 중단하고 writer를 정상 종료한다. 원래 데이터 디렉터리의 자동 재시작과 대체 경로를 차단해 후속 writer와 동시에 가동되지 않게 한다.
2. `bin/v2-journal-check -state /data/v2.jsonl -protection-registry /config/registry.json -backup-dir /backup/new-verified-copy`를 실행한다. 경로는 새 디렉터리여야 한다. 원본 잠금, 서명 재생, 복사본 재검증을 수행하며 미확인 응답 또는 복구 중간 상태가 있으면 복구용 백업을 거부한다. 성공한 출력과 `backup.json`의 파일 해시·순번·저널 head를 함께 보존한다.
3. 승계 호스트의 새 작업 경로에 복사하고, 동일한 registry 파일로 `bin/v2-journal-check`를 실행한다. 복사본의 순번과 head를 `backup.json`과 대조한다. 백업 디렉터리를 보관하려면 writer는 별도 작업 복사본으로만 시작한다.
4. 이전 writer가 중단된 상태에서만 같은 registry와 보존 한도로 새 writer를 연다. 인증과 정상·거부 응답, 정책과 감사 상태를 확인한 뒤 트래픽을 연결한다. 애플리케이션 데이터와 정책 제어 상태, registry 및 키 관리는 각 서비스의 별도 백업 절차를 사용한다.

이 절차는 정지된 V2 저널의 복사와 복구를 제공한다. 독립 디스크의 여러 writer를 조정하는 클러스터 합의와 자동 장애 전환은 별도 배포 인프라가 담당한다. 원본 저널을 보관한 채 용량을 늘리거나 자동 삭제하는 동작은 없다.

`-v2-combined-prepare`는 기존 선택형 사전 승인·응답 준비 원자 기록을 사용한다. `-reuse-protected-buffers`는 기존 32개 동시 수락 한도 안에서 응답 버퍼를 재사용하며 반환 시 전체 버퍼를 지운다. 두 옵션은 서명, 전체 본문 검증, 동기식 증거 기록, 승인, 응답 후 쓰기 기록을 유지한다. 기본값은 모두 꺼짐이다.

`-protection-metrics`는 고정된 처리 구간별 시간 히스토그램만 비공개 상태에 추가한다. 식별자·URL·토큰·본문을 포함하지 않으며 승인 판단에 사용하지 않는다. SDK 예제의 `collect_timings`도 선택형 진단이다. 성능 결과는 이 옵션들과 부하 조건을 명시하여 해석해야 한다.

계측을 켜면 비공개 상태의 `v2_timings`에서 V2 잠금 대기·검증·쓰기·동기화·회전 구간을, `coverage_evidence_storage`와 `protection_evidence_storage`에서 두 증거 저장소의 상태를 각각 확인할 수 있다.

같은 옵션으로 `coverage_evidence_timings`와 `protection_evidence_timings`도 제공한다. 두 저장소의 append·잠금 대기·직렬화·예약 진입/종료·봉인·파일 준비·쓰기·즉시 Sync·rollback·상태 조회를 16개의 고정 단계로 나눈다. snapshot 자체는 저장소 잠금이나 파일 스캔을 하지 않지만 상태 endpoint의 기존 `Stats()`는 잠금을 사용할 수 있다. 단계가 중첩되므로 합산하지 않는다. `sync`는 appendLine의 즉시 Sync만 포함하며 봉인·rollback·그룹의 지연 Sync를 포함하지 않는다. 이 경과 시간만으로 디스크 지연과 OS 스케줄링을 구분할 수 없다. 기본 설정에서는 새 진단 키를 노출하지 않는다.

동시에 갱신되는 atomic snapshot의 count와 bucket 합은 일시적으로 다를 수 있다. 단계 count는 실패 호출·배치·하위 단계를 포함할 수 있으므로 성공 요청이나 서명 행의 분모로 사용하지 않는다. 정확한 건수는 요청·원장 감사로 확인한다. 공유 budget을 연결하지 않은 구성의 `budget_enter`·`budget_exit`·`lease_allow`는 기존 nil 경로 비용이며 공유 예약이나 디렉터리 스캔을 측정한 값이 아니다.

Python `SQLiteSessionService` 예제는 생성자에 `persistent_audit_handles=True`를 지정하면 두 append 핸들을 재사용한다. 기본값은 `False`다. 응답·증명 행을 순서대로 쓰고 flush한 뒤 응답하며, 짧은 쓰기나 쓰기·flush·close 실패 시 기록기를 차단한다. SDK 로그는 flush 계약이며 fsync 또는 두 파일의 원자적 기록을 보장하지 않는다.


과거 WSL2 부하 시험의 배치 설정과 완료·중단 기록은 [공개 검증 요약](VALIDATION.md#earlier-completed-latency-qualification--2026-11-14)에 있습니다.
