# 공격 분석과 방어 전략 갱신

사용자 소유 시스템의 방어 및 방어 검증을 위한 기능이다. ARTEX의 관측·계획·실행·결과·재계획 구조를 방어 측에 적용한다. AI 모델의 가중치 학습이나 소스 코드 자동 수정은 하지 않는다.

## 활성화

기존 L3 설정의 모델 이름, digest, loopback origin을 유지하고 다음 옵션을 설정한다.

```json
{
  "bundled_context": true,
  "prefetch_observations": true,
  "adaptive_strategy": true
}
```

L3 자체는 기존 `enabled`, 모델 digest, 실행 예산 설정이 필요하다. 실제 격리는 기존 `allow_containment` 및 운영자의 `contain` 요청이 모두 필요하다. 기본값은 비활성이다. `short_references`는 함께 사용할 수 있다. Decisions 연결은 필요하지 않다.

## 갱신 동작

서명 검증을 통과해 저널에 기록된 최근 60초의 SDK 관측에서 거부된 리소스 수, 반복 범위, 정상 응답, 기타 관측을 집계한다. 이는 관측 패턴이며 공격 의도나 취약점 악용 성공의 증명이 아니다. 현재 케이스에서 보존한 최대 32개 관측을 분석하므로 전체 트래픽 비율로 해석하면 안 된다.

같은 tenant·asset·principal·session·route·method·authorization revision·registry·enforcer의 이전 정책 결과를 참고한다. 다른 사용자나 인증·신뢰 버전의 결론을 재사용하지 않는다. 결과는 모델 설명이 아니라 실제 서버 응답 기록의 격리 효과, 정상 요청 피해, 불완전 응답, 해제 후 복구를 사용한다.

- `contain_exact`에서는 반복 횟수와 최근성으로 정확한 후보의 우선순위를 정한다. 이미 활성인 범위, 같은 범위에 정상 응답도 관측된 경우, 이전 결과가 SDK에 가려 추가 효과를 입증하지 못한 범위는 재격리 후보에서 제외한다. 새로운 범위가 나타나면 그 범위를 다시 평가한다.
- 불완전한 결과는 `verify_response`, 해제·만료 후 복구가 미확인인 경우는 `verify_recovery`로 전환한다. 정상 요청 피해나 일시정지는 `review_collateral`로 전환하며 추가 격리를 제안하지 않는다. 기존 운영자 복구 절차를 따른다.
- 이미 모든 적격 범위에 대응 중이면 `verify_existing_response`, 이전 SDK 차단과 동일한 반복만 남으면 `observe_guard_baseline`으로 전환한다. 해제 후 쿨다운 중인 범위는 후보에서 제외하고 다른 후보가 없으면 `wait_cooldown`으로 전환한다.
- 모델 문맥은 최신 32개 관측으로 제한하지만, 사건 revision이 32를 넘었다는 이유만으로 영구 보류하지 않는다. 같은 사건의 보존된 검증 이벤트 수가 전체 revision과 정확히 일치할 때만 `complete_case_history`를 표시한다. 전체 보존 이력에서 최근 60초의 같은 정확한 대상 범위에 정상 응답이나 상충 결과가 있었는지도 검사한다. 누락한 관측 수는 `omitted_observations`로 제공하며 모델의 표본 수치를 전체 트래픽 수치로 해석하지 않는다. 압축·보존 정책 등으로 전체 이력을 확인할 수 없거나 현재 기타 관측이 섞인 경우는 `review_evidence`로 검토한다.
- 관련 정책 episode가 4개를 초과하면 최신 4개와 잘림 표시를 반환하고 `review_history`로 전환한다. 누락한 과거 결과를 성공으로 가정하지 않는다.

실행 직전 현재 전략과 기존 케이스 SHA·epoch·TTL·후보 조건을 같은 잠금에서 재검사한다. 분석 중 다른 대응이 설치된 경우 중복 claim을 추가하지 않고 요청을 거부한다. 현재 케이스와 전략을 조회한 뒤 새 실행 ID로 다시 검토한다.

각 L3 실행의 `strategy`는 예약 시점의 근거를 담는다. 실제 조치 후 기존 outcome 관측에서 `revised_strategy`를 기록하고 AI에도 `next_strategy`로 제공한다. 이 갱신은 추가 모델 호출을 사용하지 않는다. 이후 실행은 새 관측과 이전 결과를 반영한 전략으로 시작한다. 갱신만으로 추가 조치나 반복 추론을 자동 예약하지 않는다.

## 조회와 기록

기존 동일 출처 관리 API의 reader 또는 operator 토큰으로 다음을 조회한다.

```text
GET /v2/strategy?tenant=<tenant>&id=<case_id>
GET /v2/l3-run?tenant=<tenant>&id=<run_id>
```

조회는 모델을 호출하거나 정책을 바꾸지 않는다. 전략에는 케이스 SHA, 저널 sequence, epoch, 전략 SHA, 익명화된 정책/범위 ID 및 결과 SHA가 포함된다. SDK 원본 proof, 토큰, payload, 원본 사용자 식별자는 포함하지 않는다. short references를 사용하는 초기 모델 입력의 후보 ID는 기존 실행 전용 alias로 표시하고 원본 전략 SHA를 유지한다. 조치 후 모델에 제시되는 다음 전략은 후보 개수와 근거만 포함하며 선택용 ID를 새로 제공하지 않는다. 다음 조사는 새 케이스와 후보를 다시 확인해야 한다. 다음 전략은 추가 실행 권한이 아니다.

선택적 snapshot은 기존 저널과 retained checkpoint에 보존된다. 새 버전은 snapshot이 없는 기존 기록을 읽을 수 있다. snapshot이 기록된 새 저널은 해당 필드를 지원하는 reader가 필요하므로 이전 바이너리로 직접 되돌려 읽는 방식은 지원하지 않는다. 재시작 시 진행 중 실행을 자동 재실행하지 않는다.

## 비용과 성능의 해석

활성 범위의 중복 격리와 추가 모델 턴을 피하는 구조다. 모델 청구액 감소, 실서비스 지연 개선, 새로운 공격의 일반화 성능은 별도 측정이 필요하다. 기존 SDK가 이미 거부한 요청은 AI의 추가 차단 성과로 계산하지 않는다. 실제 모델 검증은 소유한 loopback 앱과 합성 계정·데이터에 한정한다.
